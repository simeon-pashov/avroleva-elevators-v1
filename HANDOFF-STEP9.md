# Avroleva Elevators — Handoff after step 9 (zones, day plan, building statement link)

Date: 2026-09-10. Read `HANDOFF-STEP8.md` (jobs, address search) and `ARCHITECTURE.md` §1–§3 first. Vocabulary rule kept: райони, екипи, план за деня, спирки, справка — operational only. Technicians never see money (the day plan carries no prices; the statement page is for the house manager, not the phone).

## 1. What exists now

| Area | What |
| --- | --- |
| Zones (`modules/registry`, L2) | `zone` table: name, colour, GeoJSON polygon (outer ring only), district names, position, `isDefault` ("Всички", created on first use, cannot be archived), active, soft delete. `building.zoneId` + `building.zoneManual` (office override). Assignment = point-in-polygon → district-name match → default zone; recomputed on building save, by `POST /zones/recompute` (audited) and by the cron `registry.recomputeZones` (02:15 daily). `domain/zone.ts` = pure point-in-polygon / district matching. Buildings list filters by `?zoneId=`; `BuildingDto` carries `zoneId`, `zoneName`, `zoneManual`. |
| Technician pairs (`modules/maintenance`, L3) | `technician_pair`: name, 1–3 `userIds` (active technicians, no duplicates), vehicle, `defaultZoneId`, position, active, soft delete. Owner-only writes. |
| Day plans (`modules/maintenance`) | `day_plan`: one row per (date, pair), `stops` JSONB (`PlanStop`: id, kind `check|callback|job|inspection`, refId, elevatorId, buildingId, order, plannedAt, status `planned|done|skipped`, completedAt, manual, notes), status `draft|published`, lockedAt, publishedAt, generatedAt, start lat/lng, estKm, notes. `service/plans.ts`: `generate` (candidates = elevators due that day incl. overdue, open callbacks, jobs scheduled that day, inspections due; candidates already assigned to a technician go to that technician's pair; the rest ordered nearest-neighbour from the base and split evenly; unlocked plans are merged — done / manual stops kept; locked plans untouched), `board` (`DayBoardDto` with `unplanned`), `update` (whole ordered list = reorder / add / remove; refIds validated), `moveStop` (same day only), `setLocked`, `publish` (→ `DayPlanPublished` per plan), `setStopStatus` (office, phone via sync `plan.stop`), `markStopDoneByRef` (subscriber: `VisitRecorded` of a check/maintenance visit, `CallbackClosed`, `JobCompleted` → the matching stop of that day's plan goes `done`). `domain/route.ts` = haversine, nearest-neighbour order, even chunking, sequence ETA (`dayStart` + `avgStopMinutes` per stop + legs at `avgSpeedKmh`). `settings.planning` (tenant data): baseAddress, baseLat/Lng, avgStopMinutes 25, avgSpeedKmh 25, dayStart 08:30. |
| Sync (tech app) | Pull adds `dayPlans` = my PUBLISHED plans for today and tomorrow (full replace) and `zoneId` on buildings. Push kind `plan.stop` `{planId, stopId, status: done\|skipped, at, clientOffsetMs, timestampSource, notes}` under the same `Idempotency-Key` rules. |
| Building access links (`modules/billing`) | `building_access_link`: 128-bit token (unique), scope `statement \| statement_and_visits`, createdBy, expiresAt (default 12 months), revokedAt/By, lastUsedAt, useCount, lastIpHash. `accessLinks.ts`: create (revokes the previous active link of the building), rotate, revoke, send (e-mail through notifications with the `statement_link` template, or a Viber deep link), status, `activeLinkUrl({create: true})` used by dunning e-mails and the monthly report e-mail so every mail carries the link. Every open counts (IP hash only, never the IP). |
| Public statement page | `GET /s/:token` (`http/statement.ts`, outside `/api`, rate-limited, no login): firm header with phones, address + customer, current balance, open invoices with the bank block + EPC QR (this page is explicit consent, so money shows regardless of `showPaymentOnPublicPage`), 12-month invoice/payment ledger, and with the wider scope visits / callbacks / defects + next inspection. `POST /s/:token/pay/:invoiceId` starts a hosted payment when a provider is configured. Revoked / expired / unknown token → 404 page. |
| Notifications | Template `statement_link` (email + viber_link × bg/en; variables `statementLink.url`, `statementLink.expiresAt`, `statementLink.message`); `dunning_*`, `statement_sent` and the report mail render `statementLink.url`. Appears in the template editor like the others. |
| Demo data | `demo/planning.ts`: zones "Изток" / "Запад" (polygons splitting Sofia at lng 23.33), pair "Екип 1" (seeded technicians, east zone), default zone assignment of every building. Idempotent. |
| Office UI | Settings → **Планиране** (`/settings/planning`): base point (address search + draggable pin + lat/lng), ETA parameters, **Райони** editor (table, create/edit with colour, districts and a click-to-add-vertex polygon on a Leaflet map with draggable vertices and the other zones drawn for context, archive, "Преизчисли"), **Екипи** editor (name, up to three technicians, vehicle, default zone; owner only). **План за деня** (`/plan`, nav after Ремонти): date (default tomorrow after 15:00 Sofia), zone filter, Генерирай / Публикувай / Обнови, totals strip, one column per pair in its colour (status badge with publish time, lock toggle, per-plan totals), cards with seq, kind pill, elevator, address link, contact `tel:`, ETA, leg km, label, Готово / Пропусни / Върни, ↑↓ keyboard fallback, remove; HTML5 drag-and-drop to reorder and to move between columns; "Непланирани" column with "Добави към…"; Leaflet map with a polyline per pair, numbered pins (grouped when several lifts share a point), base marker, pin click highlights the card. Dashboard due widget: "Планирай деня" link. Building page: "Достъп за домоуправителя" card (state, scope, validity, opens, last open, URL + copy, Viber deep link, send by e-mail / Viber with prefilled contact, rotate, revoke, history), "Район" in the details, "Добави асансьор тук" under the map (reuses the step-8 dialog, attaches to this building), zone select in the building form (manual override, "Автоматично" resets). ## 6. Known gaps

- Archiving a technician pair leaves its existing plans in place (they still show on the board and on the phone with the old pair name); generate ignores the archived pair, so its stops can be planned twice. A follow-up: on archive, drop the pair's draft plans (or move their stops to "Непланирани").
- Locking is a UI structure rule (no drops / reorder / remove) plus the API's "keep on regenerate"; the API itself still accepts `PATCH` on a locked plan.
- Routing is straight-line nearest-neighbour from the base; no road distances, no time windows, no return leg. `estKm` is indicative.
- Tomorrow's plan is read-only on the phone until the day comes; a plan published for today after the technician already pulled needs the next pull (open the app / pull-to-refresh).
- Zone polygons are single-ring; holes and multipolygons are ignored. District matching is exact (trimmed, case-insensitive) on `address.district`.
- The statement page has no PDF; the e-mail carries the link only. Opens are counted per request (a refresh counts again).
- `vite.config.ts` dev proxy: `/p` was a bare prefix and swallowed the SPA route `/plan` (served a stale built index); now anchored (`^/p/`), plus `^/s/` for the statement page in dev.
- Demo data: the dev tenant used for verification keeps the test pair "Екип 2", a second technician "petar", an archived test pair from an agent's smoke run and its plan for 2026-09-10 (nightly demo reset clears them).

## 7. What step 10 needs — Capacitor Android wrap of `apps/tech`

- **Absolute API base**: the PWA calls relative URLs through the Vite proxy / same-origin static mount. In a native shell there is no origin: `platform/http` must use a configurable absolute base (`apps/tech/src/platform` already has `getApiBaseOverride` / `setApiBaseOverride` from the enrollment screen — make it the single source, default it from a build-time `VITE_API_BASE`, and send `X-Client: app` + `X-Client-Version` on every call).
- **Bearer-only auth path**: device sessions today ride a cookie (same-origin). For Capacitor (`capacitor://localhost` / `https://localhost` origin) use the bearer token the enrollment already returns (`/auth/enroll` → session token) on every request and on `/sync/*`; make sure CORS allows the app origin and the cookie path is not required. Check `apps/api/src/platform/http/ctx.ts` (`authenticate`) accepts `Authorization: Bearer` for device sessions.
- **Platform interfaces**: `apps/tech/src/platform/` (http, storage, camera, geolocation, clock) — add Capacitor implementations behind the same interfaces (Camera → `@capacitor/camera`, Geolocation → `@capacitor/geolocation`, Network → `@capacitor/network` for the outbox drain trigger, App → back button / resume → `pull()`), keep the web implementation for the PWA build.
- **Service worker**: the SW (`sw.ts`, injectManifest) is for the PWA; the Capacitor build bundles assets, so guard SW registration by platform and rely on the forced-update header (`clientVersion`) for the store build.
- **Icons / splash**: `@capacitor/assets` from a 1024 px icon (the brand "A" in `apps/office/index.html`'s favicon is the only mark today) + adaptive icon + splash in brand blue; Android `minSdk` 26, `targetSdk` per Play policy; `appId` e.g. `bg.avroleva.tech`.
- **Versioning**: `apps/tech/package.json` is `0.5.0`; `APP_VERSION` (`src/version.ts`) is what the API compares (`noteClientVersion`, forced update). Keep `versionName` = package version, `versionCode` monotonic in `android/app/build.gradle`.
- **Deep links**: the office QR encodes `<origin>/tech/?enroll=<code>`; register an Android App Link / custom scheme so the QR opens the app (fallback stays the PWA URL).
- **Offline**: Dexie/IndexedDB works in the Capacitor WebView; the outbox and photos stay as they are. Test the `plan.stop` and `job.event` push after a cold start with no network.
